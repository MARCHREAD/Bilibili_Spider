# bilibili GT3 文字点选 —— 准确性与速度实测报告

测试对象：`js_reverse_cache/tasks/bili-gt3-solver`（运行路径不含浏览器/CDP/Playwright/Selenium）。
所有轮次均为**现取新 challenge**（每次请求 `passport.bilibili.com/x/passport-login/captcha`），
判决读的是服务端 `/ajax.php` 响应体本身，不是页面元素。

## 1. 准确性

| 测试批次 | 轮次 | 最终通过 | 说明 |
|---|---|---|---|
| 串行 10 轮 | 10 | 10 | 单进程顺序执行 |
| 并行 10 轮（jobs=2） | 10 | 10 | 两条独立协议链 |
| 并行 20 轮（jobs=4） | 20 | 20 | 四条独立协议链 |
| **合计** | **40** | **40** | |

最终通过率 **40/40 = 100.0%**。

所有 validate 互不相同：**True**（40 个码，证明不是复用同一会话）。
服务端返回的 score：['14']。

### 1.1 但“100%”不等于“一次就对”

极验在提交错误时会自动 `refresh.php` 换一道新题，链路会一直重试到通过，
因此**“最终通过率”会掩盖单次提交的真实命中率**。逐次提交统计如下：

| 指标 | 数值 |
|---|---|
| 统计轮次 | 20 |
| **首次提交命中率** | **12/20 = 60.0%** |
| **单次提交命中率** | **20/32 = 62.5%** |
| 平均提交次数/轮 | 1.60 |
| 一次通过的轮次 | 12 |
| 需 2 次的轮次 | 4 |
| 需 3 次的轮次 | 4 |

失败原因可归因到**提示词识别**：失败的提交里，提示词总有一个字在图片字形集合中
完全找不到（fallback 分配），而成功的提交几乎没有这种情况。

| 分组 | fallback 数/次提交（中位/均值） | 最低匹配分（中位/均值） |
|---|---|---|
| ok | 0.0 / 0.35 | 2.0 / 6.25 |
| fail | 1.5 / 1.42 | 0.0 / 1.25 |

典型失败：一轮提示词被读成 4 字 `绍义麻鸭`、`凉瑜豆粉`，实际是 3 字 `宜宾燃面`；
另有一轮读成 2 字 `藤滞`。**字数读错时必然失败**。

## 2. 速度

### 2.1 单轮延迟（串行 10 轮，同机同口径）

| 指标 | min | 中位 | 均值 | max |
|---|---|---|---|---|
| 单轮端到端 | 13.65s | **20.95s** | 23.15s | 36.69s |
| 本地求解 | 5027ms | **6779.5ms** | 6660.8ms | 7915ms |
| 最终提交往返 | 1.77s | 1.79s | 1.79s | 1.8s |
| 每轮 HTTP 请求数 | 11 | 12 | 13.4 | 17 |

> 注意：这 10 轮里有重试，会把端到端时间拉长（HTTP 请求 11→17 次）。
> **首次即成功的轮次只需 13.6–16.8s**；重试到第 3 次的轮次才会到 36.7s。

### 2.2 时间都花在哪（单轮中位数拆解）

| 环节 | 耗时 | 占比 |
|---|---|---|
| 本地求解（OCR 旋转扫描） | 6.78s | 32% |
| 驱动对每次 SDK 请求的 0.5s 固定延时 | ~6.2s | ~30% |
| 最终提交往返 | 1.79s | ~9% |
| SDK 虚拟机 + 资源下载 + 过桥通信 | ~5.5s | ~26% |

### 2.3 吞吐（并行）

| 配置 | 轮次 | 总墙钟 | 吞吐 | 单轮中位 | 求解中位 | 通过 |
|---|---|---|---|---|---|---|
| jobs=2 | 10 | 127.8s | 0.078 轮/s（282 轮/h） | 23.2s | 8017.0ms | 10/10 |
| jobs=4 | 20 | 190.8s | 0.105 轮/s（377 轮/h） | 33.26s | 15946.0ms | 20/20 |

并发下求解耗时上升（8 线程池 × 多条链争抢 CPU），但**吞吐提升且准确率不变**：
jobs=4 时 190.8s 完成 20 轮。注意这是**客户端并发能力**，不代表服务端允许的速率——
未做长时间高频压测，是否触发风控/限流尚未验证。

## 3. 本次做的性能修复：OCR 扫描并行化

剖析发现单轮耗时几乎全部在 `read_glyph`：每个字形要做
`2 pad × 36 角度 × 2 模型 × 2 尺度 = 288` 次 ddddocr 识别，每次 20–160ms，
5 个字形合计 ~1440 次调用（检测框本身只要 0.2s）。

ddddocr 分类是线程安全的（onnxruntime 释放 GIL，两个识别器只读共享），
因此把分类步骤放到线程池（默认 min(8, CPU)），旋转等预处理留在主线程：

- `gt3_click_solve_v11.read_glyph()` 改为线程池 `map`
- 线程数可用环境变量 `GT3_OCR_WORKERS` 覆盖（1 = 退回串行）

## 4. 优化前后对比（同一条命令 `python main.py --rounds 2`）

| | 优化前（本次测试开始时实测） | 优化后 |
|---|---|---|
| 第 1 轮 | 175.8s | 14.7s |
| 第 2 轮 | 176.6s | 13.9s |
| 通过 | 2/2 | 2/2 |

**单轮 ~176s → ~14s**；不过这个倍率**混入了机器负载**（优化前机器同时跑着飞书/微信/ChatGPT，
同一张图单次求解在前测中慢到 224s），不能全归功于并行化。
并行化本身的净收益请以 §3.1 为准：同进程、同图片、同一次运行内测得的 **3.0–5.2×（中位 3.67×）**。

另外注意 §2.1 的 20.95s 中位含重试轮次；**首次即成功的轮次实测为 13.6–17.7s**
（`main.py --rounds 1/2` 三次复现：14.7s / 13.9s / 17.7s，均 http=11、一次通过）。

## 5. 结论与可选后续优化

**准确性**：最终通过率 40/40 轮 = 100%；但真实单次提交命中率只有 ~62%，
首次命中率 ~60%，其余靠 SDK 自动换题重试补齐。瓶颈是**提示词字数/字符识别**，不是点击定位。

**速度**：优化后单轮中位 20.95s（其中求解 6.78s、0.5s 固定延时 ~6.2s），
首次即成功时约 14s；jobs=4 吞吐 ~377 轮/h。

后续可做（按性价比排序）：

1. **提高提示词识别稳健性**（收益最大，直接提高单次命中率）：
   字数目前靠“字段字形反验”（`anchors()`）决定，读错字数就必然失败。
   可用**硬约束**兜底：字段字形框数量是已知的，点击数 ≤ 字形框数，且每个提示字必须能
   一一对应到不同字形；再叠加第三个识别模型/更多尺度投票，专门解决 3 字被读成 2 字或 4 字。
2. **削减 OCR 冗余**：0–355° 每 10° 全扫 + 2 pad × 2 尺度共 288 次/字形，
   可先粗扫（如 30°）定位候选角度再精扫，或在低分字形上提前跳过。
3. **去掉等待**：`gt3_protocol.Session.get` 每次请求前 `time.sleep(0.5)`，
   单轮累计 ~6.2s。这是为降低风控而加的，压缩需先评估限流风险。

## 6. 复现方式

```powershell
cd js_reverse_cache\tasks\bili-gt3-solver
python main.py --rounds 2                    # 端到端，打印 validate
python check_v11.py                         # 离线标注回归（4/4）
python check_parallel_equiv.py              # 并行 vs 串行一致性 + 加速比
python bench_solver.py --rounds 10 --keep-logs --out bench_serial10.json
python bench_solver.py --rounds 20 --jobs 4 --out bench_parallel20.json
python failure_analysis.py bench_logs_serial10   # 首次命中率/失败归因
python latency_budget.py bench_logs_serial10     # 延迟拆解
python make_report.py                       # 重新生成本报告
```

`bench_logs_serial10/`、`bench_logs/bench_par2_10/`（含每轮完整 trace）、
`parallel_equiv.json`、`failure_analysis.json`、`latency_budget.json`。
